# The in-process models on ggml

anofox-decide runs its in-process models (Julia-1, Laya multilingual, Laya typed-decisions: ModernBERT / mmBERT
encoders with a decision head) on ONNX Runtime. This page tracks moving them onto the ggml engine that
anofox-tabfm runs on, shared by both extensions through `anofox-ggml-adapter`, and then removing ONNX Runtime.

Order: feature parity on the CPU, then on GPUs (CUDA, ROCm, MLX), then performance, then the removal.

| Bar | Before ONNX Runtime may go |
|---|---|
| Parity (CPU) | every real-weight golden unchanged; `test/sql/decide_local_e2e.test` green; the 200-ticket evaluation gives 0 label flips against ONNX Runtime, accuracy and AUROC identical to 3 decimals |
| Parity (GPU, fp32) | 0 label flips, probabilities within 1e-3 |
| Performance | faster (evaluation wall time) and lower peak RSS than ONNX Runtime, per model |

During the move, `SET anofox_decide_local_engine = 'ort' | 'ggml'` picks the engine (default from the
`ANOFOX_DECIDE_LOCAL_ENGINE` environment variable, else `'ort'`). It goes away with ONNX Runtime.

## Phase 0: the ONNX Runtime baseline (2026-11-23)

Machine: AMD Ryzen AI (24 threads), 46 GB, Linux; the extension from `main` at f9404ed (ONNX Runtime 1.29.0).

### Evaluation (200 Bitext tickets, two questions each, `tools/eval/run_eval.py`, catalog models)

Accuracy and AUROC reproduce `docs/EVALUATION.md` exactly. Wall time on ONNX Runtime varies about 2x between identical
runs (its own thread pool competes with DuckDB's), so the protocol is: an idle machine, warm page cache, at least three
runs per engine, alternating engines, and the best run counts. Peak RSS does not vary. Best of five runs:

| Model | Wall | CPU | Peak RSS | Refund acc / AUROC | Routing acc |
|---|---|---|---|---|---|
| julia-1 | 6 s | 119 s | 1.42 GB | 29.5% / 0.407 | 37.5% |
| laya-multilingual | 13 s | 276 s | 3.10 GB | 92.0% / 0.970 | 62.0% |
| laya-typed-decisions | 34 s | 724 s | 4.82 GB | 88.5% / 0.978 | 76.0% |

`run_eval.py` records the wall and CPU time, the peak RSS and the local engine of every model in `report.md` and
`report.json`.

```
python3 tools/eval/make_sample.py --out <dir>/sample
python3 tools/eval/run_eval.py --tickets <dir>/sample/tickets.csv --out <dir>/ort --models julia-1,laya-multilingual,laya-typed-decisions
```

The per-ticket answers (`results_cat-*.csv`) are the label-flip oracle for the ggml engine; they are kept outside
the repository with the sample (the Bitext data is not committed).

### End-to-end test

`test/sql/decide_local_e2e.test` (generated by `tools/e2e/make_local_e2e.py`): 40 repo-owned support tickets, eight of
them in German, French, Spanish, Italian or Dutch, answered by all three catalog models. Refund probability, team
routing, frustration score, a thresholded decision, `decide_answers` and `decide_many`, and cross-row batching. The
expected answers were captured from ONNX Runtime; any engine must reproduce them (1e-4, labels exact).

```
# DuckDB's unittest gives each SQL test its own HOME, so the downloaded models are passed in with DECIDE_CACHE_DIR
DECIDE_REAL_WEIGHTS=1 DECIDE_CACHE_DIR=~/.cache/anofox-decide ANOFOX_DECIDE_LOCAL_ENGINE=ort  ./build/release/test/unittest test/sql/decide_local_e2e.test
DECIDE_REAL_WEIGHTS=1 DECIDE_CACHE_DIR=~/.cache/anofox-decide ANOFOX_DECIDE_LOCAL_ENGINE=ggml ./build/release/test/unittest test/sql/decide_local_e2e.test
make e2e_local ANOFOX_DECIDE_LOCAL_ENGINE=ggml   # both E2E files and the real-weight C++ goldens; fails if anything is missing
```

The engine is required, never defaulted: each file sets it and checks with `__anofox_decide_local_sessions()` (a
development diagnostic: the cached sessions, their engine and forward passes) that this engine, and only it, answered.
A mistyped `ANOFOX_DECIDE_LOCAL_ENGINE` is an error, not a silent ONNX Runtime run.

### The user-registered path and the C++ goldens

`test/sql/decide_local_e2e_registered.test` registers full `.onnx` exports of the three models, the way a user does,
and requires them to answer exactly like their catalog twins (1e-5), including a Platt-calibrated registration. The
existing C++ real-weight goldens (`test_decide_local.cpp`, `test_decide_batching.cpp`, `test_decide_catalog.cpp
[real]`) use the same exports. They were made from the Hugging Face snapshots, whose `model.safetensors` are
byte-identical to the catalog downloads (Julia-1 at a85b127321d5, Laya at 55cf4c4ebb4e):

```
cd tools/export_julia && uv sync
uv run python -c "from huggingface_hub import snapshot_download as s; s('SupersonicLabs/Julia-1', local_dir='<dir>/weights/julia-1'); s('convaiinnovations/laya', local_dir='<dir>/weights/laya')"
echo '{"head": {"head_layers": 2, "dropout": 0.1}}' > <dir>/laya_spec.json
uv run export_julia export --spec ../../docs/julia-1-spec.json --weights <dir>/weights/julia-1 --out <dir>/out/julia-1
uv run export_julia export --spec <dir>/laya_spec.json --weights <dir>/weights/laya/multilingual --out <dir>/out/laya-multilingual
uv run export_julia export --spec <dir>/laya_spec.json --weights <dir>/weights/laya/typed-decisions --out <dir>/out/laya-typed-decisions
cp <dir>/weights/laya/multilingual/rl_agent_config.json <dir>/out/laya-multilingual/
cp <dir>/weights/laya/typed-decisions/rl_agent_config.json <dir>/out/laya-typed-decisions/
```

Environment for the real-weight tests: `DECIDE_REAL_WEIGHTS=1`, `DECIDE_EXPORTS_DIR=<dir>`,
`JULIA_WEIGHTS_DIR=<dir>/weights/julia-1`, `JULIA_ONNX=<dir>/out/julia-1/julia1.onnx`,
`LAYA_MULTILINGUAL_DIR` / `LAYA_ML_DIR=<dir>/weights/laya/multilingual`, `LAYA_ONNX=<dir>/out/laya-multilingual/julia1.onnx`,
`LAYA_TYPED_DIR` / `LAYA_TD_DIR=<dir>/weights/laya/typed-decisions`, `LAYA_TYPED_ONNX=<dir>/out/laya-typed-decisions/julia1.onnx`.
On ONNX Runtime all of them pass with nothing skipped (103 C++ cases, 2,937 assertions).

## Performance: ggml against ONNX Runtime (2026-11-24)

Same machine as the baseline (AMD Ryzen AI 9 HX 370: 12 cores, 24 threads, 46 GB), the same 200 Bitext tickets with two
questions each, the extension built from `feat/ggml-gpu`. Protocol: three rounds, engines alternating, a round starts only
when the machine's one-minute load is below 4, the best run counts.

| Model | ggml wall | ONNX Runtime wall | ggml peak RSS | ONNX Runtime peak RSS | ggml CPU | ONNX Runtime CPU |
|---|---|---|---|---|---|---|
| julia-1 | **4.7 s** | 5.4 s | **0.49 GB** | 1.45 GB | 44 s | 103 s |
| laya-multilingual | **10.7 s** | 13.0 s | **1.94 GB** | 3.13 GB | 112 s | 266 s |
| laya-typed-decisions | **25.9 s** | 30.8 s | **2.44 GB** | 4.89 GB | 296 s | 657 s |

Every ggml run was faster than every ONNX Runtime run, at about half the memory and less than half the CPU time. The
answers: 0 label flips against the ONNX Runtime oracle on all 400 answers per model, metrics identical, largest
probability difference 2.4e-5 (`tools/eval/compare_runs.py`).

**What made the difference: one engine thread per physical core.** The engine used to run with DuckDB's thread count,
here 24 (12 cores with SMT). A second thread per core adds no arithmetic, and every op ends on a barrier that waits for
the slowest thread. Measured with the evaluation's own query (`SET threads = N`, laya-typed-decisions): 34.6 s at 24
threads, 26.0 s at 16, **25.4 s at 12**, 27.6 s at 8; julia-1 5.8 s at 24, 4.7 s at 12; laya-multilingual 12.0 s at 24,
10.1 s at 12. The engine now runs `min(DuckDB threads, physical cores)` threads (`DecideLocalEngineThreads`, using the
adapter's `PhysicalCpuCores()`, which honours a taskset/cpuset).

**Contention.** A barrier-per-op engine degrades sharply when other processes compete for the cores: with a parallel
C++ build on the same machine laya-typed-decisions took 78-186 s at 24 threads, against ONNX Runtime's 31 s. The earlier
"643 s" figure for it was measured that way. Leaving the SMT siblings free also leaves headroom for such load.

Not needed for the target, so not done: F16 weights on the CPU, fused attention, shape bucketing. Per-length compiles
cost about 7 ms each (72 compiles for the 200 tickets, under 1 s of 26 s).
